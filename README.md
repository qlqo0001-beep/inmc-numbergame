# inmc-numbergame — 숫자 미니게임 모음

숫자를 소재로 한 미니게임 **10종**을 하나로 묶은 Paper 플러그인입니다.

가장 큰 특징은 **진행이 다이얼로그(Paper Dialog API)로 이루어진다**는 점입니다. 인벤토리 칸을 클릭하는 대신 서버가 그려주는 창에서 바로 입력하고 바로 결과를 봅니다. 정답은 서버 메모리 밖으로 절대 나가지 않으므로 패킷을 뜯어봐도 답을 알 수 없습니다.

예외는 두 군데뿐이고 둘 다 이유가 분명합니다 — **보상 아이템 등록**은 다이얼로그가 아이템을 받을 수 없어 인벤토리 창을 쓰고, **빠른 계산**은 창을 다시 그리느라 깜빡이면 게임이 망가져서 액션바+채팅을 씁니다. 자세한 내용은 아래 [입력 방식](#입력-방식)과 [왜 아이템 등록만 인벤토리 창인가](#왜-아이템-등록만-인벤토리-창인가)에 있습니다.

게임마다 **보상 · 랭킹 · 시즌 초기화 · 순위 보상 · 참가 조건**을 전부 인게임에서 설정할 수 있고, 설정 화면은 게임 종류를 가리지 않고 자동으로 만들어집니다.

## 요구 사항

| 항목 | 값 |
|---|---|
| 서버 | Paper **26.1** 이상 |
| Java | **25** |
| 필수 의존성 | **`inmc-core`** — 같이 배포되는 공용 런타임입니다. 이것 하나뿐이며, 이것 없이는 로드되지 않습니다. |
| 선택 연동 | Vault(돈) · PlaceholderAPI · MMOItems/MythicLib · ItemsAdder/Nexo/Oraxen/EcoItems |

선택 연동은 전부 없어도 정상 부팅·동작합니다. 연동 플러그인이 우리보다 늦게 켜져도 자동으로 다시 인식합니다.

## 빌드

```bash
./gradlew build
```

`build/libs/inmc-numbergame-1.0.0.jar` 를 `plugins/` 에 넣으면 됩니다. (`-dev.jar` 은 셰이딩 전 파일이니 사용하지 마세요.)

## 테스트 서버

```bash
./gradlew runServer
```

Paper 26.1 을 자동으로 받아 `run/` 에서 띄우고 방금 빌드한 jar 을 설치합니다. **최초 1회는** 서버가 EULA 를 요구하며 종료되므로, `run/eula.txt` 를 열어 `eula=true` 로 바꾼 뒤 다시 실행하세요. (마인크래프트 EULA 동의는 서버 운영자가 직접 해야 하는 것이라 빌드에서 자동으로 처리하지 않습니다.)

> **베팅형 2종은 기본적으로 꺼져 있습니다.** 실제 서버 화폐가 오가므로 배당과 한도를 확인한 뒤 직접 켜도록 되어 있습니다. Vault 가 없으면 목록에 아예 나타나지 않습니다.

### 같은 게임을 여러 개 만들 수 있습니다

게임의 **종류**(BASEBALL)와 **설정된 게임 하나**(`baseball3`)는 다릅니다. 관리 화면에서 `baseball5`, `updown1000`, `speedmath_hard` 처럼 원하는 만큼 만들 수 있고, 각각 **자기 보상·자기 랭킹·자기 시즌**을 가집니다.

## 입력 방식

기본은 **다이얼로그**입니다. 다만 다이얼로그에는 구조적 한계가 하나 있습니다 — **띄운 창은 수정할 수 없습니다.** 내용이 바뀌면 닫고 1틱(50ms) 뒤 새로 띄우는 수밖에 없어서, 한 판에 문제를 30번 푸는 게임은 화면이 30번 깜빡입니다.

그래서 게임마다 **입력 방식**을 고를 수 있습니다.

| 값 | 동작 |
|---|---|
| `DIALOG` (기본) | 창에 문제와 기록이 나오고, 입력란에 답을 씁니다 |
| `FAST` | 문제가 **액션바**에 뜨고(제자리 갱신 = 깜빡임 없음) 답은 **채팅**으로 칩니다 |

**빠른 계산만 기본이 `FAST`**, 나머지 9종은 `DIALOG` 입니다. 원 요구사항의 "다이얼로그가 불편하거나 애매한 경우 제외" 에 해당하는 지점이 여기 하나였습니다.

`FAST` 로 플레이하는 동안 친 채팅은 답으로 소비되어 다른 사람에게 보이지 않습니다. `포기` 또는 `quit` 를 치면 그만둡니다.

## 명령어

권한은 **`ng.admin` 하나뿐**입니다. 아래 유저용은 권한이 필요 없습니다.

| 명령어 | 설명 |
|---|---|
| `/숫자게임` | 게임 목록 다이얼로그 |
| `/숫자게임 <게임id>` | 그 게임을 바로 열기 |
| `/숫자게임 랭킹 [게임]` | 랭킹 화면 |
| `/숫자게임 우편함` | 받지 않은 보상 수령 |
| `/숫자게임 도움말` | 명령어와 지금 할 수 있는 게임 |
| `/숫자게임 관리` | 관리 다이얼로그 (`ng.admin`) |
| `/숫자게임 관리 초기화 플레이어 <닉> [게임]` | 그 사람의 일일 횟수·쿨다운 초기화 |
| `/숫자게임 관리 초기화 전체 [게임]` | **서버 전체** 일일 도전 횟수 초기화 |
| `/숫자게임 관리 시즌종료 <게임>` | 순위 보상을 지급하고 시즌 랭킹 초기화 |
| `/숫자게임 리로드` | 설정 다시 읽기 |

별칭: `/ng`, `/numbergame`, `/미니게임`

초기화 두 종류는 콘솔에서도 쓸 수 있어 자동화(예: 매일 새벽 스크립트)에 걸 수 있습니다.

### 게임별 권한

플러그인 권한은 `ng.admin` 하나지만, **게임마다 필요한 권한을 따로 걸 수 있습니다.**

기본 설정 화면의 **필요 권한** 칸에 `group.vip` 같은 노드를 적으면 그 권한이 있는 사람에게만 목록에 보이고 시작도 막힙니다. 비워두면 누구나 할 수 있습니다(기본 제공 11종 전부 비어 있습니다).

이 플러그인이 새 노드를 만들지 않고 자유 입력으로 둔 이유는, 이미 쓰고 있는 랭크 권한을 그대로 가리키는 편이 낫기 때문입니다.

### 왜 아이템 등록만 인벤토리 창인가

다이얼로그에는 **아이템을 끌어다 놓을 수 없습니다.** 그렇다고 보상을 등록하려고 `mmoitems:SWORD:EXCALIBUR` 를 손으로 타이핑하게 하면, 아이템을 들고 확인하는 방식의 장점이 전부 사라집니다.

그래서 **아이템을 집는 동작만** 인벤토리 창으로 처리합니다. 빈 칸에 아이템을 올리고 [등록] 을 누르면 등록되고, **그 보상의 확률·수량·명령어·금액·공지 여부는 다시 다이얼로그 폼 하나**에서 한 번에 입력합니다. 이것이 아이템 쪽에서 다이얼로그를 벗어나는 유일한 지점입니다.

## 설정은 어떻게 만들어지는가

게임 종류가 10가지인데 설정 화면을 10벌 만들지 않았습니다. 각 게임은 자기 설정 목록(스키마)을 선언하고, 관리 화면은 **그 목록을 읽어 입력 폼을 자동으로 만듭니다.**

- 숫자 → 슬라이더 또는 텍스트 상자
- 켜기/끄기 → 토글
- 선택지 → 드롭다운
- 시간 → `30s` `5m` `1d` 형식 텍스트

덕분에 새 게임을 추가해도 설정 화면을 따로 짤 필요가 없고, 어떤 게임이든 **모든 항목이 인게임에서 조절 가능**하다는 것이 구조적으로 보장됩니다.

값이 이상하면 예외를 던지는 대신 **기본값으로 조용히 되돌아갑니다.** 손으로 고친 YAML 에 오타가 하나 있다고 게임 전체가 안 뜨는 일은 없습니다.

## 보상

보상은 다섯 가지 시점에 지급할 수 있습니다.

| 시점 | 설명 |
|---|---|
| 참가 보상 | 게임을 시작할 때마다 |
| 클리어 보상 | 성공으로 끝냈을 때 |
| 실패 보상 | 시도 초과·시간 초과·포기 |
| 일일 첫 클리어 | 그 날 처음 클리어했을 때 한 번만 |
| 기록 구간 | "3회 이내에 맞히면" 같은 조건 |
| 순위 보상 | 시즌이 끝날 때 등수별로 |

**기록 구간은 조건을 만족하는 것이 여러 개면 전부 지급됩니다.** `5회 이내` 와 `3회 이내` 를 둘 다 만들어 두면 2회에 맞힌 사람은 둘 다 받습니다. 하나가 다른 하나를 대체하는 게 아니라 겹쳐서 쌓이는 구조입니다.

보상 하나하나는 **아이템 · 수량 범위 · 확률 · 실행 명령어 · 지급 금액 · 전체 공지 여부**를 가집니다. 아이템 없이 명령어만, 또는 돈만 주는 보상도 만들 수 있습니다.

묶음 지급 방식은 세 가지입니다.

| 방식 | 동작 |
|---|---|
| 전부 지급 | 등록된 보상이 각자 확률대로 따로 판정 |
| 하나만 추첨 | 확률을 가중치로 삼아 딱 하나 |
| N개 추첨 | 가중치로 지정 개수만큼 중복 없이 |

### 아이템 저장 방식

`inmc-urb` 와 같은 방식입니다. 보상은 기본적으로 **참조**로 저장됩니다 (`minecraft:diamond`, `mmoitems:SWORD:EXCALIBUR`, `itemsadder:ruby` …). 지급할 때마다 원본 정의대로 새로 만들기 때문에

- MMOItems 등에서 아이템을 수정하면 보상에도 바로 반영되고,
- 새로 발급한 같은 아이템과 인벤토리에서 정상적으로 겹칩니다.

이름·로어·인챈트를 손수 붙인 바닐라 아이템처럼 참조로 표현할 수 없는 것은 **스냅샷**으로 저장됩니다.

### 우편함

인벤토리가 가득 찼거나 **접속 중이 아닐 때**의 보상은 우편함에 보관됩니다. 시즌 순위 보상이 여기 쓰입니다 — 랭킹은 정해진 시각에 마감되고, 1등은 대개 자고 있기 때문입니다.

중요한 점은 **보상 추첨이 정산 시점에 딱 한 번 돌아간다**는 것입니다. 우편함에는 "보상 묶음"이 아니라 **이미 확정된 결과**가 들어갑니다. 그래서 같은 등수를 한 사람은 같은 것을 받고, 수령 시각을 골라 더 좋은 결과를 노릴 수 없습니다.

## 랭킹과 시즌

게임마다 **시즌 랭킹**과 **통산 랭킹**이 따로 유지됩니다. 초기화는 시즌 랭킹만 비우고 통산은 계속 쌓입니다.

### 순위 기준 두 가지

| 방식 | 동작 |
|---|---|
| **최고 기록** | 시즌 중 세운 가장 좋은 기록 **하나**로 순위. 많이 한다고 올라가지 않고 잘해야 올라갑니다 |
| **누적 점수** | 플레이할 때마다 점수를 쌓아 합계로 순위. 참여 유도형 |

게임별로 고를 수 있습니다. 숫자야구·업다운은 최고 기록이, 빠른 계산·베팅은 누적 점수가 어울립니다.

> 두 값은 **어느 방식을 쓰든 항상 같이 기록됩니다.** 시즌 도중에 방식을 바꿔도 아무도 초기화되지 않습니다.

### 초기화 시점

| 정책 | 설명 |
|---|---|
| `NONE` | 초기화 없음 (영구 누적) |
| `DAILY` | 매일 지정 시각 |
| `WEEKLY` | 매주 지정 요일·시각 |
| `MONTHLY` | 매월 지정 날짜·시각 (없는 날짜는 그 달 마지막 날로) |
| `INTERVAL` | 마지막 초기화로부터 지정 시간마다 |
| `MANUAL` | 관리자가 [지금 시즌 종료] 를 누를 때만 |

초기화가 오면 **순위 보상 지급 → 지난 시즌 보관 → 시즌 랭킹 비우기 → 전체 공지** 순으로 처리됩니다.

> **서버가 꺼져 있는 동안 초기화 시각이 지나가도 밀린 만큼 여러 번 돌지 않습니다.** 다음 초기화 시각을 절대 시간으로 저장하고, 처리한 뒤에는 **지금 시각 기준으로** 다시 계산하기 때문입니다. 2주간 꺼져 있던 주간 시즌은 켜질 때 **한 번만** 정산됩니다.

**최소 플레이 수**를 두면 표본 미달자는 순위 보상에서 빠집니다. 아무도 안 한 시즌에서 마지막 날 한 번 해 본 사람이 1등 상을 가져가는 것을 막습니다.

## 참가 조건

| 항목 | 설명 |
|---|---|
| 일일 플레이 횟수 | 0 이면 무제한 |
| 일일 초기화 시각 | 게임별로 지정 (기본 새벽 4시) |
| 재플레이 쿨다운 | 클리어/실패 후 다시 시작하기까지 |
| 참가비 (돈) | Vault 필요. 없으면 조용히 무시 |
| 참가비 (아이템) | 인벤토리 창에서 지정 |
| 실패 시 환불 | 기본 꺼짐 |

하루의 시작은 **서버 시계 기준**입니다. 사람마다 다른 시각에 리셋되면 설명할 수도, 서버 전체를 공평하게 초기화할 수도 없기 때문입니다.

포기해도 참가 횟수는 돌아오지 않습니다. 마음에 안 드는 문제가 나올 때마다 다시 뽑는 것을 막기 위해서입니다.

## 추첨형 게임 (로또 · 최저 유일 숫자)

이 둘은 혼자 하는 게임이 아니라 **주기마다 서버 전체를 한 번에 정산**합니다.

1. 번호를 고르고 참가 (참가비가 있으면 이때 차감)
2. 추첨 주기가 되면 자동 정산
3. 결과가 채팅으로 공지되고 등수별 보상 지급 (오프라인이면 우편함)
4. 곧바로 다음 회차 시작

번호는 마감 전까지 **몇 번이든 바꿀 수 있고, 바꾸는 데는 돈이 들지 않습니다.**

당첨 보상은 **[순위 보상] 구간을 그대로 사용합니다.**

- 로또: 6개 일치 = 1위, 5개 = 2위, 4개 = 3위, 3개 = 4위
- 최저 유일 숫자: 가장 작은 유일 숫자 = 1위, 그다음 = 2위 …

보상 편집기가 하나뿐이라 시즌 보상을 설정해 본 사람은 로또 상금표도 바로 만들 수 있습니다.

최저 유일 숫자는 **성립 최소 인원**을 둘 수 있고, 미달이면 그 회차는 무효가 되며 **참가비를 전부 돌려줍니다.**

## 진행 중이던 게임

세션은 **재접속과 서버 재시작을 넘어 유지됩니다.** 정답은 이미 뽑혀 세션 안에 있으므로 다시 뽑을 것도 없이 같은 문제가 그대로 돌아옵니다.

- 접속이 끊겨도 게임을 끝내지 않습니다 (참가비를 이미 낸 상태이므로)
- 아무 입력 없이 `session.idle-timeout` 이 지나면 정리됩니다
- 한 사람당 진행 중인 게임은 **하나**입니다. 여러 판을 벌여 놓고 제일 좋은 결과만 제출하는 것을 막습니다

**시간 제한은 "언제까지"가 아니라 "얼마나 남았는지"로 저장됩니다.** 5분짜리 게임을 2분 하다 서버가 1시간 꺼졌다 켜져도 남은 3분이 그대로 돌아옵니다. 절대 시각으로 저장하면 서버가 꺼져 있던 동안 시간이 흘러 복원되자마자 시간 초과로 죽는데, 참가비만 날리고 한 턴도 못 두는 셈이 됩니다. 경과 시간도 함께 보존되므로 랭킹의 동점 처리(소요 시간)도 정직하게 유지됩니다.

숫자 기억 게임만 예외적으로 복원 시 **숫자를 다시 보여주는 단계로 되돌립니다.** 재부팅 전에 본 숫자를 기억하라고 할 수는 없기 때문입니다.

**포기해도 그때까지 쌓은 점수는 기록됩니다.** 빠른 계산에서 20문제를 풀고 포기해도 점수는 남고, 베팅에서 잃고 있다가 포기해도 손실이 순수익 랭킹에 그대로 올라갑니다 — 지면 포기해서 손실을 숨기는 것을 막기 위해서입니다.

## 파일 구조

```
plugins/inmc-numbergame/
├─ config.yml          공통 설정 (세션·우편함·기록 보관량)
├─ messages.yml        모든 문구 (MiniMessage)
├─ games/<id>.yml      게임별 설정 — 다이얼로그가 자동으로 씁니다
└─ data/
   ├─ ranking.yml      시즌/통산 랭킹 · 다음 초기화 시각 · 시즌 번호
   ├─ seasons.yml      지난 시즌 기록
   ├─ plays.yml        일일 횟수 · 쿨다운
   ├─ sessions.yml     진행 중인 게임
   ├─ events.yml       추첨 회차와 참가 번호
   ├─ mailbox.yml      미수령 보상
   └─ stats.yml        최근 플레이 기록
```

`games/<id>.yml` 은 손으로 고쳐도 되지만, **서버를 켜둔 채 고치면 다음 저장 때 덮어써집니다.** 손편집 후에는 `/숫자게임 리로드` 를 실행하세요.

## 플레이스홀더

PlaceholderAPI 가 있으면 다음 확장이 등록됩니다.

| 플레이스홀더 | 값 |
|---|---|
| `%ng_game_count%` | 활성 게임 수 |
| `%ng_playing%` | 지금 진행 중인 게임 수 |
| `%ng_mailbox_count%` | 내 미수령 보상 수 |
| `%ng_<게임>_my_rank%` | 내 시즌 순위 |
| `%ng_<게임>_my_rank_alltime%` | 내 통산 순위 |
| `%ng_<게임>_my_best%` | 내 시즌 최고 기록 |
| `%ng_<게임>_my_score%` | 내 시즌 누적 점수 |
| `%ng_<게임>_plays_left%` | 오늘 남은 플레이 횟수 |
| `%ng_<게임>_season%` | 현재 시즌 번호 |
| `%ng_<게임>_next_reset%` | 다음 초기화까지 남은 시간 |
| `%ng_<게임>_top_name_<n>%` | n위 플레이어 이름 |
| `%ng_<게임>_top_score_<n>%` | n위 기록/점수 |

랭킹을 상시로 보여주고 싶다면 명령어보다 **스코어보드나 홀로그램**이 낫습니다. 예를 들어 스코어보드에 이렇게 걸면 됩니다.

```
&e[ 숫자야구 3자리 ]
&f1위 %ng_baseball3_top_name_1% &7- %ng_baseball3_top_score_1%
&f2위 %ng_baseball3_top_name_2% &7- %ng_baseball3_top_score_2%
&f3위 %ng_baseball3_top_name_3% &7- %ng_baseball3_top_score_3%
&7내 순위: &e%ng_baseball3_my_rank%위
&7초기화까지: &e%ng_baseball3_next_reset%
```

`rankOf` 는 보드를 정렬하지 않고 앞선 인원만 세므로 매 틱 갱신해도 부담이 없습니다.

메시지 안에서는 `{게임이름}` `{플레이어네임}` `{시도}` `{점수}` `{순위}` `{기록}` `{금액}` `{아이템}` `{시간}` `{개수}` `{수량}` `{시즌}` `{사유}` 를 쓸 수 있습니다. 영문 별칭(`{game}` `{player}` `{score}` …)도 동작합니다.

## 성능

| 항목 | 처리 |
|---|---|
| 파일 입출력 | 전부 전용 워커 스레드. **메인 스레드에서 디스크를 만지지 않습니다** |
| 반복 태스크 | **1초 주기 하나뿐.** 세션 타임아웃 · 시즌 초기화 · 추첨 · 저장을 전부 여기서 처리 |
| 조회 | 게임·랭킹·플레이 기록·우편함 모두 메모리 상주 |
| 저장 | 변경된 것만 모아 `storage.save-interval`(기본 30초)마다 한 번 |
| 순위 조회 | 정렬이 아니라 **앞선 인원 세기**(O(n)). 스코어보드가 초당 여러 번 불러도 안전 |
| 우편함 | `mailbox.expire-after`(기본 90일)가 지난 미수령 보상은 자동 정리 |

> **저장 주기를 왜 1초에서 30초로 늘렸나** — 파일 쓰기는 원래 비동기였지만 **YAML 을 만드는 작업은 메인 스레드**에서 일어납니다. 1000명 × 11종이면 초당 수만 번의 값 설정이 됩니다. 종료·리로드 시에는 주기와 무관하게 즉시 저장하고, 시즌 정산이나 보상 지급이 이 주기 때문에 사라지는 일은 없습니다.

숫자 기억 게임의 "숫자가 사라지는" 연출은 반복 태스크가 아니라 **한 번짜리 지연 작업**입니다.

## 다이얼로그를 쓰면서 주의한 것

Paper Dialog API 는 조용히 망가지는 방식이 많습니다. 아래는 전부 **실제로 당한 뒤** 막아둔 것들입니다.

1. **콜백이 메인 스레드 보장이 없습니다.** 모든 버튼 콜백은 메인 스레드로 넘긴 뒤에야 상태를 건드립니다.
2. **한 번 띄운 창은 수정할 수 없습니다.** 내용이 바뀌는 화면은 닫고 **1틱 뒤에** 새로 띄웁니다. 같은 틱에 다시 띄우면 클라이언트가 무시합니다.
3. **콜백은 기본이 1회용입니다.** 버튼을 두 번 누르면 두 번째가 죽어버리므로 횟수 제한을 풀어 두었습니다.
4. **입력 칸 이름에 하이픈을 쓸 수 없습니다.** 서버가 `StringTemplate.isValidVariableName` 으로 검사하며 **영문·숫자·밑줄만** 허용합니다. 설정 파일은 관례대로 `max-attempts` 로 두고 다이얼로그로 넘길 때만 변환합니다.
5. **`id` 는 예약어입니다.** Paper 가 콜백 UUID 를 같은 NBT 에 `id` 로 담기 때문에, 입력 칸을 `id` 로 지으면 그 값이 UUID 를 덮어써 **버튼이 아무 반응도 하지 않습니다.** 예약어는 자동으로 접두사를 붙입니다.
6. **버튼이 하나도 없는 창은 거부됩니다.** 타이머로만 넘어가는 화면이라도 버튼이 필요합니다. 비어 있으면 안내창으로 대체하고 경고를 남깁니다.
7. **구버전 클라이언트는 창이 아예 안 뜹니다.** 다이얼로그는 1.21.6+ 입니다. ViaVersion 이 있으면 프로토콜을 확인해, 지원하지 않는 클라이언트에는 조용히 무시하는 대신 안내 메시지를 보냅니다.

```bash
./gradlew test
```

엔진이 전부 Bukkit 과 무관한 순수 로직이라 서버 없이 규칙을 검증합니다 (**96개**).

**규칙**
- 숫자야구 S/B 판정 — 특히 중복 숫자를 다중도로 세는지 (`12` 에 `11` 은 1S 0B)
- 업다운 이분탐색 최소 횟수 계산
- 31 게임 필승 전략이 실제로 200판 전승하는지
- 블랙잭 에이스 1/11 처리, 52장 덱 구성
- 빠른 계산이 음수·나누어떨어지지 않는 문제를 내지 않는지
- 로또 추첨/등수 매핑/티켓 검증, 최저 유일 숫자의 중복 탈락 처리

**실제 플레이 흐름** (`GameFlowTest`) — 규칙이 맞아도 한 판이 끝까지 굴러가는지는 별개라서 따로 검증합니다
- 숫자야구를 실제로 이겨보기 / 시도 소진으로 져보기 / 거부된 입력이 시도를 안 잡아먹는지
- 업다운을 이분탐색으로 권장 횟수 안에 클리어하는지
- 빠른 계산이 세션에 점수를 쌓고 시간 종료 시 그대로 넘기는지
- 숫자 기억의 노출 → 입력 단계 전환, **복원 시 노출로 되돌아가며 제한시간이 살아나는지**
- 베팅이 정산할 금액을 세션에 올리는지, 소지금 초과 베팅이 거부되는지

**주변 장치**
- 랭킹 정렬(양방향) · 기록 구간 중첩 지급 · **`rankOf` 가 목록 위치와 항상 일치하는지**
- 완전 동점자의 순서가 매번 같은지 (순위 보상이 목록 위치로 지급되므로)
- **세션 시계** — 다운타임 뒤 남은 시간이 보존되는지, 이미 끝난 세션이 무제한으로 살아나지 않는지
- **초기화 시각 계산** — 특히 서버가 2주간 꺼져 있다 켜졌을 때 정확히 1회만 정산되는지
- 모든 게임 타입의 설정 스키마가 다이얼로그에 쓸 수 있는 형태인지
